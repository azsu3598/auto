### 2-6. 새 5회 계획 작성

새 batch 계획 JSON 규칙(`infra/paper_batch.py`의 `validate_batch`·`parent_reference` 기준):

- `sessions`는 정확히 5개, 연속 거래일. `batch_id`와 각 `pilot_id`는 새 32자리 소문자 16진수(이전 값 재사용 시 거부).
- **첫 회차 `entry_date`는 이어 붙일 회차의 `exit_date`(2026-11-03)보다 뒤여야 한다.** 같은 날은 거부된다. 두 번째 회차부터는 기존처럼 앞 회차 `exit_date`와 같아야 한다.
- 첫 회차 09:45 GATE 전에 `DEPLOYMENT_CHECK`가 실행돼야 하므로, 배포·검사 일정을 고려해 시작일을 사용자와 정한다.
- `parent` 형식:

  ```json
  "parent": {
    "kind": "stopped_batch_session",
    "session_index": <옛 운용 sessions 배열에서 entry_date가 2026-11-02인 마지막 항목의 0부터 센 번호>,
    "prefix": "validation/batch/<중단한 운용 batch_id>",
    "plan_key": "<중단한 운용 불변 계획 S3 키>",
    "plan_sha256": "<그 파일의 SHA-256>",
    "batch_plan": { "...중단한 운용 계획 전체, 수정 금지..." }
  }
  ```

- `session_index`는 정수여야 하며 범위를 벗어나거나 `true`·`"1"`이면 거부된다. **실제 계획 파일을 열어 번호를 확인한다.** 추정하지 않는다.
- 스택 파라미터 `ParentPrefix`=`prefix`, `ParentPlanKey`=`plan_key`. parent 회차 판단 파일 `runs/2026/11/02/KRX_1520/decision.json`을 새 스택이 읽을 수 있는지 `DecisionKey` 권한을 확인한다.
- 사전 검증(morning proof) 값은 사용자와 확인한다.
- 오프라인 검사:

  ```cmd
  "C:\Test\.venv\Scripts\python.exe" tools\paper_batch_checks.py --plan <계획 파일>
  ```

  기대 출력: `BATCH_PLAN_AND_SCHEDULE_BOUNDS: PASS; NO_AWS_CALLS; NO_MUTATIONS`

### 2-7. 배포와 시작

- 기존 관리자 절차와 사용자 승인으로 스택을 갱신하고 `DEPLOYMENT_CHECK`를 실행한다. 기대 결과 `DEPLOYMENT_VERIFIED`.
- 새 형식에서 `DEPLOYMENT_CHECK`·첫 GATE가 확인하는 것:
  - 중단한 운용 루트에 `STOP.json`이 `STOPPED_BY_OPERATOR`와 `at`으로 있어야 한다(없으면 `PREDECESSOR_OPERATOR_STOP_REQUIRED`).
  - 루트 `HALT.json`은 없거나, `reason=BATCH_MANUALLY_STOPPED`이고 STOP 이후 시각이어야 한다(아니면 `PREDECESSOR_BATCH_HALTED`).
  - parent 회차 이후 회차에 `START_PM`/`START_AM`/`SCAN_1450`/`SHORTLIST_1510`/`ENTRY_1520`/`EQUITY_SNAPSHOT_1550`/`EXIT_0905`/`EXIT_0910` 실행 기록이 없어야 한다. `BATCH_MANUALLY_STOPPED`로 차단된 기록과 `GATE`는 허용(아니면 `PREDECESSOR_LATER_SESSION_STARTED`).
  - parent 회차 자체는 기존과 같이 전 단계 완료·실제 lease·판단/장부 일치·최종 보고 깨끗함·**ledger digest 일치**·서버 정지를 확인한다. parent 회차 폴더의 `STOP.json`은 계속 거부한다.
- 예약 활성화(ARMED)는 사용자 승인 후 기존 절차로 한다.
