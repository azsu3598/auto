## 0. 먼저 알아야 할 것

- PC-D는 코드만 작성했다. **테스트는 한 번도 실행되지 않았다.** 이번 PC-C 작업의 목적은 테스트로 검증하는 것이다.
- 지금 AWS에서는 5회 모의운용(마지막 청산 11/03)이 **진행 중**이다. 이번 작업에서 AWS는 절대 건드리지 않는다.
- 이번에 바뀐 코드 요약:
  1. 15:10 시세가 0건이면 15:20 사유를 "기준 충족 종목 없음"이 아니라 "시세 자료 없음"으로 남긴다 (`src/stock_automation/aws_runtime.py`).
  2. 텔레그램 알림 아래에 한국어 설명을 붙인다 (`infra/paper_batch.py`, `src/stock_automation/notifications.py`, `infra/paper_control.py`).
  3. 모의운용 회차 수로 5회뿐 아니라 **2회**도 허용한다 (`infra/paper_batch.py`, `tools/paper_batch_checks.py`, `tools/paper_operations.py`).
  4. 새 운용의 직전 회차(parent)로 **이전 운용의 마지막 회차**를 쓸 수 있다 (`infra/paper_batch.py`의 `parent_reference()`).

## 1. 절대 하지 말 것

- AWS 명령 실행, 스택 생성·업데이트, 예약(Scheduler) 켜기/끄기, ECR push, Lambda 갱신 **금지**.
- `stop` 명령 실행 금지. 진행 중인 5회 운용을 멈추는 명령이다.
- 테스트를 통과시키려고 **안전 검사 코드를 지우거나 약하게 바꾸기 금지**. 예: 회차 수 검사 제거, HALT/STOP 확인 제거, `ledger_digest` 비교 제거.
- 실패한 테스트를 지우거나 `skip` 처리하거나 기대값을 실패 결과에 맞춰 고치기 **금지**.
- `paper_pilot.py` 수정 금지. 이미 끝난 단회 운용 코드다.
- 공동 인수인계의 기존 기록 수정 금지. 새 기록만 맨 위에 추가한다.
- `LIVE_ORDER_ENABLED`, 비상정지, 실계좌 Secret 관련 변경 금지.
- `git add .` 금지. commit/push는 사용자가 요청할 때만 한다.

## 2. 해야 할 일 (이 순서대로)

모든 명령은 Windows **CMD**에서 실행한다. PowerShell이나 WSL을 쓰지 않는다.

### 2-1. 최신 코드 받기와 문서 읽기

```cmd

git status --short
git pull
git log --oneline -3
```

- `git status --short`에 출력이 있으면 pull하지 말고 **멈춘 뒤 사용자에게 파일 목록을 보고**한다.
- pull 후 `AGENTS.md` → `PC-C_단독진행_전체인수인계.md` → `Codex_세션간_공동_인수인계.md`를 끝까지 읽는다.

### 2-2. 5회차 운용 템플릿 재생성

`infra/paper_batch.py`가 바뀌어서 저장된 템플릿 파일도 다시 만들어야 한다. 이 명령은 파일만 만들고 AWS를 호출하지 않는다.

```cmd
cd /d C:\Test\stock-automation
"C:\Test\.venv\Scripts\python.exe" tools\build_paper_batch_template.py --output infra\paper-five-session-batch.yaml
```

- 기대 출력: `FIVE_SESSION_BATCH_TEMPLATE_BUILT; disabled; no AWS calls`
- 바뀌어야 하는 파일은 `infra/paper-five-session-batch.yaml` 하나뿐이다. `git status --short`로 확인한다.
- 다른 템플릿(`paper-one-session-pilot.yaml`, `paper-control.yaml` 등)은 다시 만들지 않는다.

### 2-5. 실패했을 때

- 하나라도 실패하거나 에러가 나면 **코드를 고치지 말고 멈춘다.**

- 가상환경은 저장소 루트의 `C:\Test\.venv`다(`stock-automation` 안이 아님).
- 예외: `C:\Test\.venv`가 없거나 패키지가 없어서 import 자체가 안 되는 경우에만 `"C:\Test\.venv\Scripts\python.exe" -m pip install -r tools\requirements.txt`로 의존성을 설치하고 다시 실행해도 된다. 설치했다는 사실도 기록한다.

## 3. 나중에 할 일 (지금 하지 않음 — 11/03 이후, 사용자 승인 후)

아래는 참고용이다. **사용자가 따로 지시하기 전에는 실행하지 않는다.**

1. 5회 운용의 최종 결과(11/03 09:40 REPORT_AM)와 HALT/STOP이 없는지 확인한다.
2. 새 앱 이미지 빌드·ECR 게시. 이미지에는 `aws_runtime.py`·`notifications.py` 변경과 9d08d91 변경이 들어간다.
3. 새 2회 운용 계획을 만든다. 핵심 규칙:
   - `sessions`는 정확히 2개. 첫 회차 `entry_date`는 이전 5회 운용의 마지막 `exit_date`(2026-11-03)와 같아야 한다.
   - `batch_id`와 각 회차 `pilot_id`는 새로 만든 32자리 소문자 16진수. 이전 운용의 ID를 재사용하면 거부된다.
   - `parent`는 아래 형식이다. `batch_plan`에는 이전 5회 운용의 **불변 계획 JSON 전체**를 그대로 넣는다(수정 금지).

     ```json
     "parent": {
       "kind": "batch_session",
       "prefix": "validation/batch/<이전 5회 운용 batch_id>",
       "plan_key": "<이전 5회 운용 불변 계획 S3 키>",
       "plan_sha256": "<그 파일의 SHA-256>",
       "batch_plan": { "...이전 5회 운용 계획 전체..." }
     }
     ```

   - 스택 파라미터 `ParentPrefix`는 위 `prefix`, `ParentPlanKey`는 위 `plan_key`와 같아야 한다.
   - 이전 마지막 회차의 판단 파일(`runs/2026/10/30/KRX_1520/decision.json` 형식)을 새 스택이 읽을 수 있는지 `DecisionKey` 권한을 확인한다.
   - 사전 검증(morning proof) 값을 무엇으로 둘지는 사용자와 확인한다.
4. `tools\paper_batch_checks.py --plan <계획 파일>`로 오프라인 검사를 통과한 뒤에만 배포를 검토한다.
5. 배포·예약 활성화는 기존 관리자 절차와 사용자 승인으로만 진행한다.
