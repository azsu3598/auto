# 5거래일 모의운용 완료 후 작업계획

작성일: 2026-10-23 / PC-C. 모든 시각은 한국시간(KST).
이 문서는 후속 작업계획이며 실거래 활성화·실계좌 키 연결·주문 승인이 아니다.

## 1. 현재 운영과 일정

- 일회성 재검증: 10/26 진입 판단, 10/27 청산. AWS 예약15개 활성화 및 재조회 확인 완료.
- 별도 후속5회: 사용자 관리자 CloudShell 출력에서 `DEPLOYMENT_VERIFIED`, `FIVE_SESSION_BATCH_ARMED; 15/15 verified` 확인. 작업 계정의 v3 조회는 AccessDenied이므로 관리자로 실행한 결과가 현재 근거다.
- 후속 진입일: 10/27, 10/28, 10/29, 10/30, 11/2. 각각 다음 거래일09:10 잔여 모의수량 청산. 마지막 청산은11/3, 마지막 보고 예정은09:40.
- 재검증1회와 후속5회는 별도다. 부모 운용이 정상 종료되지 않으면 후속 신규 진입을 막는다. 오류 발생 시 HALT를 임의 해제하거나 실행 기록을 삭제하지 않는다.
- 주문은 프로그램 내부 가상 장부에만 기록한다. 증권사 모의 주문·체결 및 실제 주문의 통합검증 성공을 뜻하지 않는다.
- 활성화 성공은 미래 예약 준비 완료다. 실제5회 운용 성공·수익 발생은 아직 확인되지 않았다.

## 2. 5회 완료 판정 기준

11/3 09:40 이후 아래 자료를 실제 AWS 기록과 대조한다. 날짜가 지났거나 텔레그램 알림을 받았다는 이유만으로 통과 처리하지 않는다.

| 확인 대상 | 완료 기준 |

| 일별 실행 | GATE, 기동, 스캔, 후보선별, 진입판단, 총자산 집계, 청산, 종료, 보고가 해당 일자·계획ID로 연결됨 |
| 판단 | 각 회차의 BUY 또는 NO_TRADE에 근거가 있으며 S3 결정과 DynamoDB 가상 장부가 일치함 |
| 청산 | 생성된 가상수량은 계획대로 청산되고 마지막 열린 수량0. NO_TRADE도 정상 완료 가능 |
| 금액 | 지갑·매수/매도·비용·손익·총자산을 대사하고 설명되지 않는 차액0 |

| 종료 | 작업·중계 서버 정지 확인, 실행/대기 작업0, 청산 종료 보고 확인 |

중단된 회차나 NO_RECORD는 완료5회에 포함하지 않는다. 정상 NO_TRADE는 포함하되 전부 NO_TRADE라면 매수·보유·매도 경로는 실제 운영에서 미검증으로 남긴다. 수익률이나 매수 횟수를 통과 조건으로 삼지 않는다.

## 3. 완료 직후 우선 작업

1. 관리자 CloudShell 실행증거 `paper-batch-v3-arming-evidence.json`과 S3·DynamoDB·CloudWatch 결과를 확보한다. 기존 상태조회 도구가 새 batch-v3와 새 계획을 실제로 추적하는지 먼저 확인하고, 과거 pilot 전용 출력으로 대체하지 않는다.
2. 5회 결과표, 가상손익, NO_TRADE 이유, 오류·재시도, 최종 포지션·서버 상태를 정리한다. **각 동작마다 결과와 함께 한국어로 발생 이유를 설명한다.** 예: `NO_TRADE`는 어떤 필수 조건이 충족되지 않았는지, `BUY`/`SELL`은 어떤 판단 근거와 시세·원장 기록으로 수행됐는지, `HALT`는 어떤 오류가 신규 진입을 차단했는지 실제 로그·결정 자료에 근거해 적는다. 자료에 이유가 없으면 추정하지 않고 `근거 기록 없음`으로 표시한다. 원본은 Git 제외 runtime에 보관하고 비밀값 없는 요약만 `docs/운영 검증/2026-11-03_5거래일_모의운용_검증.md`에 작성한다. 실제 검증일이 달라지면 그 날짜를 쓴다.
3. `통과 / 추가 모의 필요 / 전환 불가`로 판정하고 증거·미검증 경로를 명시한다. 운영 완료는 전략 수익성이나 실거래 안전 전체를 입증하지 않는다.
4. 기간이 끝난 예약이 추가 실행을 만들지 않는지, 서버가 정지했는지 확인한다. 추가 모의 일정 생성·연장은 사용자 요청 없이 하지 않는다. 기록·지갑·자원은 임의 삭제하지 않는다.

### 2026-10-26 단회 모의운용 NO_TRADE 사유 분류 보완

- 10/26 기록에서 14:50·15:10 스캔은 시세 36건을 받았고, 15:10 후보 목록은 0건이었다. 15:20 입력 스냅샷은 빈 후보 목록 때문에 시세 배열도 비었으며, 기존 분류가 이를 `MARKET_DATA_UNAVAILABLE`로 잘못 표시했다.
- 판단 엔진은 선행 후보 선별 완료 후 빈 목록으로 진입한 경우 `NO_QUALIFYING_CANDIDATE`와 한국어 사유를 남기도록 수정했다. 후보가 존재하지만 현재 시세를 받지 못한 경우의 `MARKET_DATA_UNAVAILABLE`는 유지했다. 후보·위험 필터와 진입·중지 보호는 바꾸지 않았다.
- 이 수정은 소스만 바꾼 상태로, 현재 ECS 이미지에는 아직 반영되지 않았다. 적용 전 새 이미지 빌드·게시와 이미지 digest를 지정한 템플릿 반영이 필요하다. AWS 작업은 별도 적용 단계에서 진행하며 본 수정에서는 배포·예약 변경을 하지 않았다.

## 5. 실거래 준비: 미리 가능한 작업

현재 `live_cli.py`, `live_execution.py`, `live_broker.py`에 주문 준비/승인/실행, 계좌 기준선, 대사, 감독 로직이 존재한다. 처음부터 전부 미구현이라고 가정하지 말고 실제 코드를 검토한다. 존재 여부와 실제 키움/AWS 통합검증 완료 여부를 분리한다.

1. 기존 실거래 안전 기능과 테스트의 누락 검토: 계좌 고정, 기존 사용자 보유분 보호, 주문 승인 유효기간, 주문/일 손실한도, 중복·동시 실행 차단.
2. 가짜 키움 응답으로 부분체결·거부·미체결·취소·응답 유실·재시작 복구·잔고 불일치를 검증한다. 응답 불명 시 자동 재주문하지 않는지 확인한다.
3. `LIVE_ORDER_ENABLED=0`과 비상정지 상태로 잠긴 실거래 전용 AWS 템플릿·최소 권한·로그·운영/복구 안내를 준비한다. 모의 지갑·포지션·성과와 실거래 상태를 분리한다. 작성은 허용되지만 배포·키 연결은 별도 승인 단계다.
4. 실제 증권사 주문·체결·잔고의 검증 계획과 비용·중지·복구 절차를 작성한다. 프로그램 내부 가상체결 결과를 증권사 검증 증거로 쓰지 않는다.
5. 변경에 맞는 집중 테스트와 전체 회귀 테스트를 실행하고 미확인 항목을 남긴다. 테스트 통과를 실거래 활성화로 간주하지 않는다.

## 6. 별도 사용자 승인 후 가능한 단계

1. 대상 실계좌, 총투입금, 주문별 상한, 일 손실한도, 주문 방식, 시험 기간, 중지·복구 조건을 구체적으로 제시하고 승인받는다. 대화에 계좌번호나 키를 요구하지 않는다.
2. 승인된 범위에서 실제 계좌 읽기 연결과 기준선·대사를 검증한다. 실계좌 Secret 연결도 별도 승인 범위로 확인한다.
3. 실거래 전용 AWS 배포·단발 시험 계획을 검토한다. 실주문·취소가 가능한 명령은 읽기 검사처럼 실행하지 않는다.
4. 실제 주문 검증이 필요한 항목은 사용자가 승인한 소액·한정 횟수로 수행한다. 이를 거치기 전 증권사 체결·취소·잔고 통합검증 완료라고 주장하지 않는다.
5. 증거 검토 후 정기 실거래 예약 활성화를 다시 승인받는다. 모의 예약을 실거래로 자동 전환하지 않는다.
