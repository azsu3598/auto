# PC-C 협의 사항 — 현재 운용 종료와 새 5회 운용 시작 일정 (2026-10-27 작성, 10-28 갱신)

> 작성: PC-D / Claude. 대상: 사용자와 PC-C 작업자(Codex 또는 Claude).
> 실행 절차의 원본은 [2026-10-27_PC-C_작업지시_운용중단_5회재시작.md](2026-10-27_PC-C_작업지시_운용중단_5회재시작.md)다.
> 이 문서는 그 절차를 PC-C와 협의할 때 알아야 할 **일정·자동/수동 구분·제약**을 정리한 것이다. 내용이 다르면 작업지시서와 코드가 우선한다.
>
> **10/28 갱신:** 처음에는 10/28 낮에 현재 운용을 중단할 계획이었으나, 사용자 일정상 불가해 PC-C 2026-10-27 21:30 기록대로 현재 5회 운용을 끝까지 마친 뒤 전환하기로 했었다.
>
> **10/28 재갱신(사용자 결정):** 새 메시지를 하루라도 빨리 보기 위해 **11/02(월) 낮에 `stop`하고 같은 날 새 운용을 배포**한다. 현재 운용의 5회차(11/02 진입)는 시작하지 않고 끝나며, 새 운용은 4회차(10/30 진입, 11/02 청산)에 이어 붙는다. 10/28~11/02 오전에는 PC에서 AWS 접속이 불가하고, 모바일 콘솔 수동 stop은 하지 않는다. 아래 일정은 이 기준이다. 회차 날짜는 문서 기록(5회차 진입 11/02)과 `infra/paper-calendar-2026.json`(이 기간 휴장 없음)으로 계산했으므로 당일 실제 계획 파일과 `status`로 다시 확인한다.

## 1. 결론

- 현재 5회 운용은 4회차까지 진행한다. 4회차는 10/30 진입, **11/02 09:40 최종 보고**로 끝난다.
- **11/02(월) 09:41~14:40** 사이에 `stop`으로 운영자 종료 표식을 남긴다. 이 시점에 5회차(11/02 진입)는 끊긴다(사용자 결정).
- 새 운용은 **5회(5거래일), 11/03(화)·11/04(수)·11/05(목)·11/06(금)·11/09(월) 진입**이다. 마지막 청산·보고는 11/10(화) 09:40이다. 처음 3회로 정했으나 같은 날 사용자 결정으로 5회로 바꿨다. 조건 확인과 실거래 준비 판단용 5회 완료를 한 운용으로 묶기 위해서다. 병행 작업은 [2026-10-28_실거래까지_병행작업계획.md](2026-10-28_실거래까지_병행작업계획.md)를 따른다.
- **11/02 안에** 배포·`DEPLOYMENT_CHECK`·예약 활성화까지 끝내야 한다. 11/03 09:45 GATE 전에 끝나지 않으면 첫 회차가 시작되지 않는다. 끝내지 못하면 첫 진입일을 뒤로 미룬 새 계획으로 다시 준비한다.
- 종료 표식과 새 운용 시작은 **자동으로 이어지지 않는다.** PC-C에서 사람이 실행하고 AWS 단계마다 사용자 승인을 받는다.

## 2. 일정

| 시각 | 내용 | 자동/수동 |
|---|---|---|
| ~11/02 09:40 | 현재 운용 1~4회차 진행·완료 | 자동(기존 예약) |
| 11/02 09:41~14:40 | `tools\paper_operations.py status` 확인 후 `stop`. **14:40 `START_PM` 전이어야 한다** | 수동(PC-C, 승인) |
| 11/02 `stop` 이후 | 새 앱 이미지·control Lambda·batch 스택 반영, 새 5회 계획 작성·검사, `DEPLOYMENT_CHECK`, 예약 활성화 | 수동(PC-C, 단계별 승인) |
| 11/03 09:45 | 새 운용 1회차 준비 검사(GATE) | 활성화 후 자동 |
| 11/03 15:10 | 후보 축소와 DART 당일 공시 조회(결과를 `shortlist.json`에 저장) | 자동 |
| 11/03 15:20 | 매수 판단(DART 호출 없이 15:10 결과 재사용) | 자동 |
| 다음 거래일 09:10 | 청산, 이후 5회차(11/09 진입, 11/10 청산·09:40 보고)까지 같은 흐름 | 자동 |

## 3. `stop`이 필요한 이유와 시각 제한

- 새 운용은 직전 운용의 정상 완료된 회차에 이어 붙는다. 이번에는 4회차(10/30 진입)다.
- 직전 운용 도중에 이어 붙이는 형식은 `stopped_batch_session`뿐이고, 이 형식은 옛 운용 루트의 `STOP.json`(`STOPPED_BY_OPERATOR`)을 필수로 요구한다.
- 새 첫 진입일은 parent 회차 청산일(11/02)보다 **뒤**여야 한다. 그래서 가장 빠른 시작이 11/03이다.
- `stop`은 09:40 4회차 `REPORT_AM`이 끝난 뒤여야 한다. 그 전이면 4회차가 미완료로 남아 parent로 쓸 수 없다.
- `stop`은 14:40 5회차 `START_PM` 전이어야 한다. 그 뒤면 5회차 실행 기록이 생겨 `PREDECESSOR_LATER_SESSION_STARTED`로 거부된다. 5회차 09:45 `GATE` 기록과 `BATCH_MANUALLY_STOPPED`로 차단된 기록은 허용된다.
- `session_index`는 옛 운용 계획에서 `entry_date`가 **2026-10-30**인 항목의 번호다. 실제 계획 파일을 보고 정한다.

## 4. 미리 준비할 때의 제약

| 항목 | 미리 해도 되는가 | 제약 |
|---|---|---|
| 새 앱 이미지 빌드·ECR 게시 | 된다 | 운용 중인 스택의 이미지 digest는 `stop` 전까지 바꾸지 않는다. 바꾸면 현재 운용 준비 검사가 막혀 HALT될 수 있다 |
| 새 5회 계획 작성·오프라인 검사 | 된다 | 첫 진입일 11/03. parent 계획의 SHA-256은 실제 S3 파일로 계산한다 |
| `stop` | **11/02 09:41~14:40만** | 09:40 전이면 4회차가 미완료, 14:40 이후면 5회차가 시작돼 이어 붙일 수 없다 |
| 새 batch 스택 갱신·`DEPLOYMENT_CHECK`·활성화 | **`stop` 이후만** | 새 코드는 옛 운용 루트에 `STOP.json`이 있어야 통과한다(`PREDECESSOR_OPERATOR_STOP_REQUIRED`) |

## 6. 새 운용의 종가배팅 판정 (`closing-v0.3`과 10/28 점검 수정)

- 촉매는 필수 조건이 아니라 점수다. DART 당일 공시가 있으면 검증 촉매로 인정한다.
- 당일 위험 공시(감사의견·상장폐지·관리종목·거래정지·자본잠식·유상증자 등 희석·횡령/배임 등)가 있으면 `DART_RISK_DISCLOSURE`로 **탈락**한다. 중기 전략과 같은 위험 목록이다.
- DART 조회는 15:10에만 하고(최대 12종목, 45초 상한), 15:20에는 저장된 결과를 재사용한다. 15:10~15:20 사이 새 공시는 반영되지 않는다.
- DART 조회에 실패하거나 상한에 걸린 종목은 위험 확인 없이 촉매 점수 0으로 남는다(사용자 결정: 당일 공시만 확인하고 진행).
- ETF·ETN은 후보에서 뺀다. DART 상장 코드가 있으면 그것만으로 판단하고, 없을 때만 이름 규칙을 쓴다.

## 7. 오늘 S3 확인 범위

- 사용자 결정: 과거 탈락 사유 집계는 **2026-10-27 하루만** 본다.
- PC-C 21:30 기록에 10/27 로컬 재적용 결과가 있다: ETF 23개 제외 후 13종목, 하드 필터 통과 0(NXT 8, 가격 2, 종가 강도 2, 거래량 1). 그날은 촉매보다 **ETF와 NXT 종목이 후보 대부분을 차지한 것**이 더 큰 원인이었다.
- 새 운용부터는 15:10마다 `shortlist.json`에 탈락 사유(`rejection_counts`)와 DART 결과(`dart_checks`)가 기록된다.

## 8. 이번 운용에 포함되지 않는 것

- 뉴스 기반 촉매 자동수집.
- NXT 대상 종목 허용(현재 KRX 전략은 NXT 대상 종목을 제외한다. 바꾸려면 별도 결정).
- 실거래 활성화·실주문·비상정지 해제·실계좌 Secret 연결. 별도 승인 대상이다.
