# 연속 단타 AWS 운영 설계 및 예상비용

> 작성 기준: 2026-10-13 KST  
> 상태: **향후 구현안**. 현재 프로그램은 `DAY_TRADE_ON_DEMAND` 단발 모의 스캔만
> 구현되어 있으며, 이 문서는 연속 감시가 이미 작동한다는 뜻이 아니다.

## 1. 결론

장중 단타를 실제 기능으로 운영하려면 한 번 실행하고 종료하는 단발 스캔이 아니라
거래일마다 장중 세션을 계속 유지하는 구조가 맞다. 권장 운영 형태는 다음과 같다.

- KST 08:50 서버·프로세스 시작 및 키움 모의 연결 점검
- KST 09:00~15:30 시장 감시
- KST 14:50 이후 신규 진입 중지
- KST 15:10까지 단타 포지션 의무 청산
- KST 15:30~16:00 원장 대사·총자산 기록·로그 정리 후 종료
- AWS 서울 리전 `EC2 t3.medium`, `gp3 20GB`, 고정 공인 IPv4 사용
- 예상 월 운영비 **약 22,000~27,000원**, 안전 예산 상한 **30,000원**

현재 Fargate 예약형 구조는 종가배팅과 중기전략에는 적합하지만 장중 연결을 유지해야
하는 연속 단타에는 맞지 않는다. 연속 단타를 구현할 때는 단타 세션을 EC2로 옮기고,
같은 시간대에 기존 단발 Fargate 작업과 중복 실행하지 않도록 실행 주체를 하나로
통합해야 한다.

## 2. 현재 구현과 목표 구조의 차이

| 구분 | 현재 구현 | 향후 연속 단타 목표 |
|---|---|---|
| 실행 방식 | 요청 시 ECS Fargate 1회 실행 | 거래일 장중 EC2 프로세스 연속 실행 |
| 실행 단계 | `DAY_TRADE_ON_DEMAND` | 별도 장중 세션 상태기계 필요 |
| 감시 대상 | 한 번 수집한 후보 | 저빈도 전체 스캔 후 후보 연속 감시 |
| 가격 처리 | 실행 시점 스냅샷 | 실시간 시세와 주기적 최신성 검사 |
| 진입·청산 | 모의 후보 평가 중심 | 모의 진입·손절·익절·당일청산 자동 처리 |
| 장애 복구 | 작업 재실행 단위 | 연결 끊김, 재시작, 중복 실행, 오래된 시세 복구 |
| 네트워크 주소 | Fargate 작업마다 바뀔 수 있는 공인 IP | 키움 등록용 고정 공인 IPv4 |
| 구현 상태 | 기본 코드 존재 | 미구현·미검증 |

## 3. 전체 종목 감시 방식

코스피·코스닥 전체 종목을 모두 실시간 정밀 감시하는 방식은 사용하지 않는다. 키움
API 제한과 서버 부하를 고려해 아래처럼 2단계로 나눈다.

1. 전체 종목 저빈도 1차 검색
   - 거래대금, 등락률, 거래량 증가, NXT 제외, 가격 및 시장 상태로 후보를 줄인다.
   - 조건검색 또는 묶음 조회를 사용하되 호출 제한을 넘지 않도록 속도를 제한한다.
2. 후보 종목 실시간 정밀 감시
   - 조건검색 결과는 최대 100종목 이내로 유지한다.
   - 실제 실시간 등록은 여유를 두고 20~50종목부터 시작한다.
   - 5분 20이평, VWAP, 돌파 유지, 거래량 증가, 기관·프로그램 수급과 촉매를 평가한다.
   - 후보가 탈락하면 실시간 등록을 해제하고 새 후보로 교체한다.

키움 공식 안내에서 확인할 운영상 제한은 다음과 같다. 실제 구현 직전 공식 문서와
모의환경에서 다시 확인한다.

- 계좌당 동시 접속 세션과 접근 토큰 운용 제한
- 실시간 시세 등록은 세션당 최대 200종목
- 국내 실시간 조건검색은 최대 10개
- 조건검색 결과는 최대 100종목
- REST 조회 호출 제한은 모의와 실계좌가 서로 다름

따라서 `전체 종목 저빈도 선별 → 100개 이하 후보 → 20~50개 정밀 감시`가 현실적인
초기 구조다. 호출 제한 응답, 시세 지연 또는 실시간 연결 끊김이 발생하면 신규 진입을
즉시 중지하고 기존 포지션의 안전 청산만 처리한다.

## 4. AWS 권장 구성

```text
EventBridge 또는 Lambda 시작/종료 예약
                |
                v
EC2 t3.medium + 고정 공인 IPv4 + gp3 20GB
  ├─ 장 시작 전 키움 모의 인증·거래일·비상정지 점검
  ├─ 전체 종목 저빈도 스캐너
  ├─ 후보 실시간 감시기
  ├─ 단타 모의 진입·손절·익절·당일청산 상태기계
  ├─ 연결 끊김·시세 지연·중복 프로세스 감시
  └─ 15:30 이후 원장 대사와 종료
        |
        ├─ DynamoDB 온디맨드: 지갑·포지션·결정·멱등 키·제어 상태
        ├─ S3: 원본 스냅샷·재생자료·운영 보고서
        ├─ Secrets Manager: 키움 모의 키와 알림 비밀값
        └─ CloudWatch/Telegram: 상태·오류·모의체결 알림
```

초기에는 NAT Gateway, Application Load Balancer, RDS/Aurora, OpenSearch를 추가하지
않는다. 대량 1분봉·5분봉을 장기 저장하고 복잡한 SQL 백테스트가 실제로 필요해질
때만 PostgreSQL을 분석용으로 검토한다. 단타 운영 상태 저장만으로는 DynamoDB면
충분하다.

### 고정 IP가 필요한 이유

키움 REST API는 허용 IP 등록을 전제로 운용한다. 현재 CloudFormation은 Fargate
작업에 `AssignPublicIp: ENABLED`를 사용하므로 작업 재시작 때 공인 IP가 달라질 수
있다. 이 구조를 연속 단타에 그대로 사용하면 등록 IP 불일치 위험이 있다.

연속 단타용 EC2에는 고정 공인 IPv4를 연결하고 키움에 그 주소만 등록한다. IP 변경,
다중 서버 동시 실행 및 같은 계정의 중복 세션을 차단한다. 키움 등록 IP와 실제 외부
IP가 다르면 프로그램은 주문뿐 아니라 모의 진입도 시작하지 않는다.

## 5. 월 예상비용

가정:

- AWS 서울 리전
- 환율 `USD 1 = KRW 1,500`
- 월 22거래일
- 거래일당 약 6.5시간의 EC2 과금, 월 약 143시간
- `t3.medium` 시간당 약 USD 0.052라는 예산 가정 사용
- 고정 공인 IPv4는 월 내내 보유

| 항목 | 계산 또는 범위 | 월 예상비용 |
|---|---:|---:|
| EC2 `t3.medium` | 0.052달러 × 143시간 × 1,500원 | 약 11,200원 |
| EBS `gp3` 20GB | 저장공간 상시 보유 | 약 2,500~3,000원 |
| 고정 공인 IPv4 | 0.005달러 × 약 730시간 × 1,500원 | 약 5,500원 |
| Secrets Manager | 비밀값 수와 호출량에 따라 변동 | 약 1,200~1,800원 |
| CloudWatch·S3·DynamoDB | 초기 소량 사용 가정 | 약 500~2,000원 |
| 세금·환율·오차 여유 | 사용량에 따라 변동 | 약 2,000원 내외 |
| **합계** | 초기 모의 연속감시 기준 | **약 22,000~27,000원** |

AWS 가격, 환율, 로그량과 데이터 요청량에 따라 달라지므로 확정 견적은 아니다.
AWS Budgets 경보는 20,000원, 점검 경보는 25,000원, 월 상한은 30,000원 수준으로
설정한다. 비용이 예상치를 넘으면 서버를 계속 켜두지 말고 로그량, 공인 IP, 중복
Fargate 작업과 데이터 호출량부터 확인한다.

### 비용 중복 방지

연속 단타 EC2를 도입한 뒤 기존 종가배팅·중기·일일 총자산 Fargate 작업을 같은
시간대에 그대로 돌리면 중복 비용과 중복 판단 위험이 생긴다. 다음 중 하나로
실행권한을 단일화해야 한다.

- 장중에는 EC2 한 대가 세 전략의 필요한 단계를 실행하고 기존 예약은 비활성화한다.
- 또는 단타만 EC2가 담당하고, 나머지 Fargate 작업은 전략·지갑·실행 잠금을 통해
  절대 같은 작업을 중복 수행하지 않게 한다.

초기 권장은 첫 번째 방식이다. 단, 전략별 자금·점수·포지션·성과 원장은 계속
분리한다.

## 6. 연속 단타 필수 상태기계

```text
STOPPED
  → PRECHECK
  → MARKET_WATCH
  → CANDIDATE_WATCH
  → PAPER_POSITION_OPEN
  → PAPER_EXITING
  → RECONCILING
  → STOPPED

오류 발생 시 어느 상태에서든 SAFE_HALT
```

필수 안전 조건:

- 프로세스 단일 실행 잠금과 세션 ID
- 거래일·시장시간·서버 KST 시각 확인
- 키움 모의계좌 및 등록 IP 확인
- 시세 최신성, API 호출 제한, 연결 상태 감시
- 시장 급락·변동성 과다 시 `NO_TRADE`
- 14:50 이후 신규 진입 금지
- 5분봉 확인 손절과 별도 비상 하드 스톱
- 15:10까지 단타 포지션 의무 청산
- 재시작 시 DynamoDB 열린 포지션과 브로커 상태 대사
- 중복 주문·중복 포지션 방지 멱등 키
- 알 수 없는 상태에서는 자동 재주문 금지
- 기존 계좌 보유종목은 절대 매도하지 않고 프로그램 원장 수량만 관리
- 실거래 비활성화, 비상정지 기본 ON 유지

## 7. 구현과 검증 순서

현재 PC-C 우선순위인 기존 140개 테스트, Docker, 키움 모의 읽기 진단, 예약 비활성
AWS 배포와 5거래일 종가배팅 검증을 먼저 끝낸다. 그 뒤 사용자가 연속 단타 구현을
별도로 승인한 경우에만 다음 순서로 진행한다.

1. 연속 세션 상태기계와 단일 실행 잠금을 모의전용으로 구현
2. 가짜 시계·가짜 시세로 장 시작, 끊김, 재시작, 장 마감 테스트 추가
3. 키움 모의 API 호출 제한과 실시간 등록·해제 통합검증
4. EC2 시작·종료 자동화와 고정 IP·비용 경보 구성
5. DynamoDB 재시작 복구와 S3 재생자료 검증
6. 단타 전용 모의자금으로 최소 5거래일 연속 운영
7. 체결률, 슬리피지, 최대낙폭, 장애·중복 여부를 검토
8. 기준 미달이면 규칙 수정 후 모의기간을 다시 시작

실거래는 이 설계의 구현과 모의검증이 끝났다는 이유만으로 활성화되지 않는다.
실계좌·계좌 지문·프로그램 전용 보유수량·주문·부분체결·취소·대사·비상정지의 별도
통합검증과 사용자의 명시적 승인이 모두 필요하다.

## 8. 현재 PC-C가 해야 할 일

이 문서 작성 시점에는 연속 단타 인프라를 배포하지 않는다. PC-C에서는 기존 단발
모의 구조를 먼저 검증한다.

- 140개 전체 테스트와 Docker 빌드
- 키움 모의 읽기 전용 진단
- 모든 예약이 `DISABLED`인 AWS 최초 배포
- `DAY_TRADE_ON_DEMAND` 단발 모의 통합검증
- CloudWatch·S3·DynamoDB·대시보드 결과 일치 확인
- 종가배팅 중심 5거래일 모의운용
- 연속 단타 구현 요청을 받기 전에는 EC2와 고정 IP를 생성하지 않음
